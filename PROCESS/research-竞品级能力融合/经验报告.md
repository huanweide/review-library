# 经验报告 · 竞品级功能深度夜间迭代（2026-11-07 夜）

## 一句话

**「库层全绿」是最容易骗过自己的时刻；真正难的是把能力接到用户手边，并且升级时不弄坏旧行为。**

## 一、这轮最值钱的三件事

### 1. 判别测试比功能清单更能定位真问题
critic 没有停在「竞品有 X 我们没有」的清单层面，而是写了**真实探针**：起两个 `server.js` 进程指向同一临时 `LIBRARY_ROOT`，并发各 POST 6 本书 → `POST 成功数= 12 /12` 但 `index.json 实际本数= 10`。这条 P0 如果只靠读代码，很可能被一句「Node 单线程同步写不会交错」轻轻放过（单进程内确实不会），但 README 明确允许四种运行方式共用同一 `library/`，多进程是**真实入口**。

同理，重复交卷探针打印出 `第1次 lapseCount=1 … 第3次 lapseCount=3`、`leechCount=2`——一次做错被记成三次，两个知识点被误标为顽固薄弱点。有具体数字才能写判别测试，才能证明修好了。

### 2. 升级时弄坏旧契约，比没做新功能更糟
本轮增加 6 个能力后，第一次 Oracle Gate 是 **单测 85/7、e2e 165/3**。三条根因全是**我自己改了用户可见的旧语义**：
- Again 从「当天可复习」变成「7 小时后」，直接打断「今日复习卷」；
- 用 stability 折算 box，破坏薄弱地图「连续答对逐级升盒」；
- 新 UI 复用了 `.search` / `.empty` 类，抢走旧 `querySelector` 的目标。

**没有一条是通过放宽测试解决的**：前两条改产品（保留旧契约、新状态量并存），第三条改新 UI 用专用类。判别测试锁新能力、回归测试锁旧契约，两套都得跑，红一条就先问「是不是我动了用户可见行为」。

### 3. 融合不是「把竞品全抄一遍」
R/C/N 闸门挡掉了 5 项看着很高级的东西：FSRS 的 ML 权重拟合（单机没有复习历史可拟合，抄了就是假装）、考试日期排程（与既有 due 队列重叠）、PDF 批注（要重写渲染层、偏笔记工具）、云同步（与零云端定位冲突）、Obsidian md 双链文件体系。

特别记一笔：**曾经整体打回过「双链体系」，差点把「知识点可视化」一起埋掉**。这次 F3 做的是分析结果内的关系图，不改落盘格式，并同步修订了 README 里那句约定——根因段 B 要求「只修 B，问题会不会再出现」，如果只补 UI 不改约定，下次评审还会以「保持轻量」为由删回去。

## 二、可复用的做法

| 做法 | 为什么有效 |
|---|---|
| 阶段零用 `gh api repos/<owner>/<repo>` 拿真实 star，而不是引用二手文章 | 外部判据可逐字符复核；`mochi-solutions/mochi` 查到 404 就明确标「二手来源，不作锚点」 |
| 新能力先写独立纯模块（`lib/srs|search|graph|analytics|cloze|backup.js`） | 判别测试能先红后绿，不必等 UI 全部接好才知道逻辑对不对 |
| 四层 API 镜像一次性接通（server / main / preload / api-client） | 避免「本地服务能用、桌面版点不动」；e2e 跑 HTTP 模式，打包版验证跑 Electron 模式 |
| 新 UI 一律用专用 class，不复用旧通用 class | 旧代码里大量 `querySelector('.search')` / `querySelector('.empty')`，同名即回归 |
| 大改动后立刻跑**全量**单测 + e2e，不挑着跑 | 7 条 SRS 单测 + 3 条 e2e 回归都是全量跑才暴露的 |
| 打包产物里解出 lib 再跑行为验证 | 防「只修了源码、用户拿到的 exe 没修」 |

## 三、还没做好的（下次优先）

1. 反馈五问仍只写 localStorage，既没落盘也不参与排程——是「数据全在本地」承诺的一个缺口。
2. 四档自评目前挂在批改结果页，没有独立的「先揭示再自评」闪卡流；竞品的主动回忆体验更完整。
3. 全局搜索是顺序扫描，上千本书时需要倒排索引或缓存。
4. 考试日期驱动排程、PDF 批注高亮按 R/C/N 打回，但属于竞品真实能力，产品要再上台阶时得重新评估。
