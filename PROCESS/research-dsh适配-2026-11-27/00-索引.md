## 这份研究解决什么

用户的原话是「去做 DSH 适配，学习 GitHub 相似资源项目，万字拆解别人的项目优点」。
按 maxloop 铁律，动手改 DSH 插件之前必须先回答「合格的插件适配长什么样」——
不是先改代码再说。所以本目录先产出基准拆解，再产出升级计划，最后才动代码。

## 一句话结论（推导过程见正文，不是空降）

外部标杆的共同做法是「**把契约做成机器可校验的单一真源 + 静态资源走命名空间/通配入口 + 配置错误在加载期暴露**」；
我们的 DSH 插件前三件里第一件做对了（action enum 从 `core/capabilities.js` 派生），后两件缺。
最硬的真缺口不在外部对比，在本地亲验：**APP_FILES 漏列 5 个前端模块 + tool 分派漏接 3 个新 action**——
这正好解释「为什么面板新功能在 DSH 里会 404 / 不可用」。详见 `03-DSH真缺口清单.md`。
