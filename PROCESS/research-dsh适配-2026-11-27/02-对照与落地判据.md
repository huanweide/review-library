## 一、对照表：它有什么 / 我们有什么 / 缺什么

| 维度 | 外部基准（逐字符证据见 01） | 我们（review-library v1.8.0） | 缺什么 / 判定 |
|---|---|---|---|

## 二、本地真缺口（Chair 亲验，逐条带锚点）

> 这些不是从外部硬套的，是拿外部基准的眼睛看本地代码看出来的。每条都有文件:行号。

### G1 · DSH tool 分派漏接 3 个新 action（最硬）

- **锚点**：`plugins/dsh-review-analysis/index.js:298` 声明 `action: { enum: ACTIONS }`（15 个，从 `core/capabilities.js` 派生）；
  但 `execute` 里的分派只到 `:326-432` 的 list/create/add/analyze/get/practice/quiz/due/attempt/rate/mark/compose，
  最后 `:432` 直接 `throw new Error('不支持的 action：' + action + '（可用 ' + ACTIONS.join('/') + '）')`。
- **对照基准**：Anki `.proto` 一处定义、各端生成；MCP 同一 schema 注册+运行共用。
- **现象**：enum 告诉模型「支持 cards/structure/snapshot」，模型一调就返回「不支持的 action」。
  这是**声明与行为不一致**，比「没做」更坏——用户以为能做，实际报错。
- **R/C/N**：R 合理（契约一致性是插件本分）／C 正确（逐字符锚点如上）／N 必要（不修就是假能力）。
  **通过，列为 P0。**

### G2 · DSH APP_FILES 漏列 5 个前端模块

- **锚点**：`plugins/dsh-review-analysis/index.js:76-83` 的 `APP_FILES` 停在 2026-11-21，只有 16 项；
  实际 `workbench/src/` 有 17 个源 + `index.html`/`manifest`/`sw.js`/`icons` 等。
  漏的 5 个：`src/study-hint.mjs`、`src/map-viewport.mjs`、`src/reader.mjs`、`src/structure-layer.mjs`、`src/exam-pack.mjs`。
- **代码里自己的警告**：`:81` 注释「少列一个模块，DSH 侧栏里的应用就是 404 白屏（不是降级，是缺文件）」。
- **对照基准**：Koishi 通配入口 + 目录解析，新增文件不改路由。
- **现象**：DSH 侧栏里做题思路按钮、导图缩放、就地阅读器、结构层、考点包全部 404；
  而 v1.8.0 真机统一验收 14/14 是在 HTTP 形态跑的，没覆盖 DSH 形态 → 漏检。
- **R/C/N**：R 合理／C 正确（目录清单实测）／N 必要（404 是硬故障）。
  **通过，列为 P0。**

### G3 · 判别只测「集合相等」，不测「每个 action 真能调用」

- **锚点**：`tools/check-dsh-adapt.mjs:117` 通过 23/0，B4 只 `/src\/llm-config\.js/.test(SRC) && /src\/overview\.mjs/.test(SRC)`——
  测的是两个老模块在不在，**没有任何一条测新增 5 模块、也没有测 15 个 action 逐个可分派**。
- **对照基准**：MCP 同一 schema 注册+parse；Anki `just check` 全量构建。
- **现象**：G1/G2 存在但判别全绿 = 假绿。这正是 maxloop「单测绿≠用户路径通」的最贵教训。
- **R/C/N**：R 合理／C 正确／N 必要（不修判别，下次还会漏）。
  **通过，列为 P0。**

### G4 · APP_SHARED_MINDMAP 分支缺路径穿越校验

- **锚点**：`plugins/dsh-review-analysis/index.js:523` 起的共用导图模块注册，
  与 `:500-514` 的 APP 资源分支不同，没有 `file.startsWith(appRoot)` 类校验。
- **对照基准**：Koishi `if (!filename.startsWith(this.root) ...) return ctx.status = 403`。
- **现象**：潜在越权读文件。不是已发生事故，但防护不该有洞。
- **R/C/N**：R 合理／C 正确（源码可见）／N 必要（安全面不能留洞）。
  **通过，列为 P1。**

### G5 · resolveProjectRoot 失败诊断太笼统

- **锚点**：`plugins/dsh-review-analysis/index.js:31-54` 四级解析，各级 `fs.existsSync` 静默跳过，
  失败只 throw「未找到统一核心目录：请配置...」。
- **对照基准**：Cordis `ValidationError` 带路径；Koishi Schema 描述+默认值。
- **现象**：DSH 用户配错时不知道是哪一级断的，排查靠猜。
- **R/C/N**：R 合理／C 正确／N 必要（诊断改善，低成本）。
  **通过，列为 P1。**

### G6 · kind / rating 参数缺 enum 约束

- **锚点**：`plugins/dsh-review-analysis/index.js:307` `kind` 是裸 string 描述、`:305` `rating` 是裸 integer。
- **对照基准**：MCP `z.enum(["error","success","debug"])` 注册+运行共用。
- **现象**：模型可能传 `kind:"考点大全"` 或 `rating:5`，到运行期才报错。
- **R/C/N**：R 合理／C 正确／N 必要（低成本防猜值）。
  **通过，列为 P1。**

### G7 · tool 描述没标读写属性

- **锚点**：`plugins/dsh-review-analysis/index.js:286-293` 描述列了 action 但无 readOnly/destructive 提示。
- **对照基准**：MCP `readOnlyHint` / `destructiveHint`。
- **现象**：模型可能把 `analyze`（贵、有副作用）当只读随手调。
- **R/C/N**：R 合理／C 正确／N 必要（纯文案，零风险）。
  **通过，列为 P0（低成本）。**

## 三、否决清单（过不了 N 关的，明确不做）

| 候选优点 | 为什么不做 |
|---|---|
| 通配入口改造（Koishi 式 catch-all） | 需要 DSH 宿主 API 从 `kind:'exact'` 换成通配支持，我们控制不了宿主；当前补清单 + 判别足够。列为 KNOWN-LIMITATION。 |
| Cordis `replace()` 热替换 | 我们没有热重载实际故障，10 个 effect 已符合逆序清理规范。不为对齐而改。 |
| required/optional 依赖声明 | `inject` 数组工作正常，无实际故障。声明层升级不产生用户可见收益。 |
| 按宿主 capability 裁剪端点 | DSH 各版本端点能力相同，没有需要裁剪的场景。 |
| 非本机 Origin 一律 403 | DSH 宿主内嵌面板的 Origin 形态未验证，改严可能挡住自己的面板。先验证再动。 |
| DejaVu 式 git-like 快照仓 | 本地单机、数据量小，5 份全量快照够用。过度工程。 |
| 加密 / AES | 本地备考数据，无跨设备同步场景。无需求。 |
| 导图撤销重做 | 用户没提，已有「恢复模型结构」粗粒度回退。不为凑功能加。 |
| 考点包回导 | 单向导出已诚实标注，无回导需求。 |

## 四、从拆解到升级：落地结果（v1.8.1，2026-11-28 已发版）

七条通过 R/C/N 的改动**全部落地**，按优先级：

- **P0**（真故障/假绿）：G1 tool 分派补 3 action ✅ → G2 APP_FILES 补 5 模块 ✅ → G3 判别升级测「逐 action 可分派」+「清单覆盖目录」✅ → G7 tool 描述标读写 ✅。
- **P1**（防护/诊断）：G4 路径校验 ✅ → G5 解析诊断 ✅ → G6 参数 enum ✅。
- **P2 明示不做**：见第三节否决清单，未做就是未做。

**验收判据（Oracle Gate 五条，逐条填）**：
(a) 命令真跑：`run-tests` 30/30、十三组判别全绿、DSH 判别 38/0——输出已贴；
(b) 过 lint：`node --check plugins/dsh-review-analysis/index.js` 通过；
(c) 真实入口可达：判别里真注册 tool 并真调 15 个 action，无「不支持的 action」；
  五个新模块经 HTTP 全 200；**DSH 宿主环境未运行，宿主内点验未做**（诚实留红）；
(d) 修复前失败输出：把旧版 index.js 临时放回跑判别 = 26/11 红（11 条新判别全红），
  修复后 38/0 绿——判别有分辨力；
(e) 逐字符锚点：每条缺口带 `index.js:行号`，外部基准带 README 原文 + URL + star + 日期。

**判别设计教训（写进来防止再犯）**：第一版 F 组对 15 个 action 全部 `execute()`，
`create` 收到空 title 会 fallback 成「未命名书」真建库——跑两轮建了 4 本垃圾书（已清理）。
测「可分派」的判别必须零副作用：只读 action 真调（行为层），写 action 查源码分派分支（声明层），
并加一条「判别不建书」的自检。这是「判别本身污染被测系统」的新型假绿/假红源。

**baseline 教训**：三份 v1.8.0 判别用 `git show HEAD:` 当 baseline，HEAD 一发版前移就假红。
统一改为固定 commit `7876189`（v1.7.3），与 `check-dsh-adapt` 固化夹具同一原则。
