## 第零节 · 为什么要拆这些项目（先讲基准逻辑，再讲结论）

我们的对象是 `复习资料图书馆` 的 DSH 插件 `plugins/dsh-review-analysis/index.js`。它不是一个独立引擎，
而是主项目 `core/` 的第四个入口：注册一个工具 + 在宿主 webServer 上挂一组端点 + 用宿主静态资源能力托管
workbench 面板。要回答「它做得够不够好」，不能自己定标准——先搜三类外部基准：

1. **宿主插件框架怎么做生命周期与依赖注入**（Cordis / Koishi）——回答「我们的插件注册/清理/配置声明对不对」。
2. **工具协议怎么做能力契约**（MCP servers）——回答「我们的 action enum、参数校验对不对」。
3. **知识资源库怎么做数据落盘与备份**（SiYuan / Anki / Logseq / Obsidian）——回答「我们的数据不丢与开放导出对不对」。

外加两个可视化基准（markmap / mind-elixir）用于导图层。三类基准 + 可视化，共 9 个真实项目。

## 第一节 · 宿主插件框架：cordiverse/cordis（10,064★）

**证据锚点**
- 全名与重定向：`api.github.com/repos/cordisjs/cordis` 返回 `"full_name": "cordiverse/cordis"`，`"html_url": "https://github.com/cordiverse/cordis"`。URL：https://github.com/cordiverse/cordis
- Star **10,064**（2026-11-27 GitHub REST API 经代理 7890 实取；另一独立研究员同日读数 10,065，差 1 为实时增长）。
- 根 README 原文逐字：
  > "A Meta-Framework of Spatiotemporal Composability."
  > "**Cordis is under active development. The API is not yet stable and may change without notice.**"
- 依赖注入源码 `packages/core/src/registry.ts` 逐字：
  > "export type Inject<M = Dict> = (keyof M)[] | { [K in keyof M]?: M[K] }"
  > "inject(deps: Inject, callback: Component.Function<void>): Fiber & PromiseLike<Fiber>"
  > "Config?: StandardSchemaV1<any, T>"
- 热插拔源码同文件逐字：
  > "replace(oldComponent: Component, newComponent: Component): Fiber[]"
- 生命周期源码 `packages/core/src/fiber.ts` 逐字：
  > "export const enum FiberState { PENDING, LOADING, ACTIVE, FAILED, DISPOSED, UNLOADING, }"
  > "INACTIVE_EFFECT: 'cannot create effect on inactive context',"
  > "await Promise.all(this._disposables.clear().reverse().map(async (dispose) => {"

**优点拆解（它怎么做 → 解决什么问题 → 我们学什么）**

1. **依赖声明从「import 别人」改成「声明我需要什么」。**
   它怎么做：`inject` 可以是键数组，也可以是 `{ [K]?: M[K] }` 形式（可选依赖），内核用 epoch 编码「依赖实现是否就绪」，依赖变化即 `_setEpoch`。
   解决什么：插件不必自己写 try/catch 降级——服务没就绪时插件挂起（PENDING），服务恢复自动重载。解耦粒度是「能力」而不是「模块」：换个数据库实现，依赖它的插件毫无感知。
   我们学什么：我们的 `export const inject = ['tools', 'webServer']` 只是名字数组，没有「必需/可选」区分，也没有就绪状态可观察。当前靠 `ctx.effect` 延迟注册兜住了，但不是显式契约。可评估声明为 `{ required: [...], optional: [...] }`。

2. **配置用 StandardSchemaV1 在注册期校验。**
   它怎么做：`Config?: StandardSchemaV1<any, T>`，注册期 `validate(config)`，失败抛 `ValidationError` 并带路径。
   解决什么：配置错误在加载那一刻暴露，不会变成运行到一半的幽灵 bug。
   我们学什么：我们的 `resolveProjectRoot` 四级解析靠 `fs.existsSync` 静默跳过，最后才 throw 一句笼统错误。应该给出逐路径诊断（config 给了什么、env 给了什么、戳记在哪、推导到哪），让 DSH 用户一眼看懂哪一级断了。

3. **热替换不重启：`replace()` 保留原 fiber 只换 runtime。**
   它怎么做：`RegistryService.replace()` 保留原 fiber，替换 runtime 与 inject，`emit('internal/replace')`。
   解决什么：改插件不重启宿主，已注册资源随 fiber 迁移。
   我们学什么：我们的 10 个 `ctx.effect` 注册会在卸载时逆序 dispose（符合官方语义），但没有 replace 语义。热重载时是整段销毁再重建，理论上有 404 空窗。这是 P2，不急着改。

4. **清理按逆序、并发执行、顺序依赖要塞进同一个 effect。**
   它怎么做：`this._disposables.clear().reverse().map(async (dispose) => ...)`，官方明确「存在顺序依赖的清理步骤必须放进同一个 ctx.effect() 返回的处置器中」。
   解决什么：卸载不残留、不死锁。
   我们学什么：我们 10 个 effect 各自只有一个注册、无跨 effect 顺序依赖，符合规范。**这一条是「做对了」的证据，不是待办。**

## 第二节 · 宿主插件框架：koishijs/koishi（6,361★）

**证据锚点**
- 全名 `koishijs/koishi`。Star **6,361**（2026-11-27 GitHub REST API；独立研究员读数 6,360，实时 ±1）。URL：https://github.com/koishijs/koishi
- README 原文逐字：
  > "Koishi 是一个跨平台、可扩展、高性能的聊天机器人框架。"
  > "超过 3000 个官方和社区插件覆盖了机器人开发的方方面面，从平台支持、数据库、资源存储、网页控制台、状态管理到具体的业务功能一应俱全。"
  > "模块热重载：开发 Koishi 插件时，只需轻点保存即可热重载，无需频繁重启机器人，如同前端开发一样丝滑顺畅"
- 依赖声明 `koishi-plugin-github/src/index.ts` 逐字：
  > "static inject = { required: ['database', 'server'], optional: ['assets', 'puppeteer'], }"
- 配置声明同文件逐字：
  > "export const Config: Schema<Config> = Schema.object({"
  > "path: Schema.string().description('GitHub 服务的路径。').default('/github'),"
- 路由与静态资源 `koishijs/webui/plugins/console/src/node/index.ts` 逐字（`koishijs/console` 重定向到 `koishijs/webui`，41★）：
  > "this.layer = ctx.server.ws(config.apiPath, (socket, request) => {"
  > "ctx.server.get(uiPath + '(.*)', async (ctx, next) => {"
  > "const filename = devMode ? '/vite/@fs/' + local : uiPath + '/@plugin-' + key"
  > "if (!filename.startsWith(this.root) && !filename.includes('node_modules')) { return ctx.status = 403 }"
- 服务文档 `koishi.chat/guide/plugin/service.html` 逐字：
  > "对于整体依赖的服务,使用 inject 属性声明依赖关系"
  > "对于部分功能依赖的服务,使用 ctx.inject() 注册为子插件"

**优点拆解**

1. **required / optional 分离的依赖声明。**
   它怎么做：`static inject = { required: [...], optional: [...] }`，可选依赖运行时 `if (ctx.assets)` 检测。
   解决什么：必需依赖缺失就挂起，可选依赖缺失不阻塞——契约机器可校验，控制台还能自动生成配置表单。
   我们学什么：同上，把我们的 `inject` 数组升级为显式必需性声明，并把 `projectRoot` 作为必填配置可见化（现在藏在四级解析函数里）。

2. **静态资源走「命名空间 + 通配入口 + 前缀校验」，不逐文件列清单。**
   它怎么做：一条 `ctx.server.get(uiPath + '(.*)')` catch-all 统一入口，按 `@plugin-<key>` 命名空间分发，再 `startsWith(this.root)` 校验，不合法 403。
   解决什么：多插件共存路径不冲突；宿主只要一条路由；**新增资源文件不需要改路由清单**。
   我们学什么：这是最硬的一条。我们用 `kind:'exact'` 逐文件注册 `APP_FILES`（固定 16 项），每加一个前端模块都要手改清单，漏一个就是 DSH 侧栏 404 白屏。代码注释里我们自己写过「少列一个模块，DSH 侧栏里的应用就是 404 白屏（不是降级，是缺文件）」——恰好印证这个设计的脆弱性。可借鉴：把固定清单降级为「白名单校验」，路径从目录按需解析。

3. **路径穿越防护无例外分支。**
   它怎么做：`filename.startsWith(this.root)` 不通过直接 403，只给 `node_modules` 一个明确例外。
   解决什么：插件不能读宿主任意文件。
   我们学什么：我们的 APP 资源分支有 `file.startsWith(appRoot)` 校验，方向对；**但共用导图模块 `APP_SHARED_MINDMAP` 那条分支没有同等前缀校验**，要补。

## 第三节 · 工具协议：modelcontextprotocol/servers（92,294★）

**证据锚点**
- 全名 `modelcontextprotocol/servers`。Star **92,294**（2026-11-27 GitHub REST API，与独立研究员读数一致）。URL：https://github.com/modelcontextprotocol/servers
- README 原文逐字：
  > "This repository is a collection of *reference implementations* for the [Model Context Protocol](https://modelcontextprotocol.io/) (MCP), as well as references to community-built servers and additional resources."
  > "The servers in this repository are intended as **reference implementations** ... not as production-ready solutions. Developers should evaluate their own security requirements ..."
  > "**Every server in this repository serves stdio by default, and every one can also serve Streamable HTTP** on `http://127.0.0.1:3001/mcp`"
- 工具 enum 契约 `src/everything/tools/get-annotated-message.ts` 逐字：
  > "messageType: z.enum([\"error\", \"success\", \"debug\"]).describe(\"Type of message to demonstrate different annotation patterns\"),"
  > "inputSchema: GetAnnotatedMessageSchema,"
  > "readOnlyHint: true, // This tool only returns data, no side effects"
  > "destructiveHint: false, // Does not delete or modify anything"
- 能力清单单一真源 `src/everything/tools/index.ts` 逐字：
  > "const capabilities = server.server.getClientCapabilities() || {};"
  > "if (capabilities.roots !== undefined) registerGetRootsListTool(server);"
- 安全边界 `src/everything/README.md` 逐字：
  > "Both HTTP transports (Streamable HTTP and HTTP+SSE) accept browser requests only from a localhost origin ... A request carrying any other `Origin` is refused with `403 Forbidden`."

**优点拆解**

1. **同一份 schema 既注册又运行时校验。**
   它怎么做：Zod schema 同时做 `inputSchema` 注册和 `GetAnnotatedMessageSchema.parse(args)`，enum 值既约束文档又约束执行。
   解决什么：不会出现「文档说三档、代码走第四档」的契约漂移。
   我们学什么：我们的 `action.enum: ACTIONS` 已从 `core/capabilities.js` 派生，方向一致。但 `kind`（digest/syllabus）和 `rating`（1-4）还是裸 string/integer 描述，模型可能猜值。可补成 enum。

2. **按宿主声明的 capabilities 决定注册哪些工具。**
   它怎么做：`getClientCapabilities()` 判断 roots/sampling 是否存在，再注册对应工具。
   解决什么：不注册对端根本不支持的工具，同一套代码服务不同协议代际。
   我们学什么：我们的 manifest 由 `core/app-host.js` 派生，是单一真源；但 DSH 侧没有「按宿主能力裁剪端点」的逻辑。这是 P2。

3. **默认只绑本机 + 非本机 Origin 一律 403。**
   它怎么做：HTTP 默认 127.0.0.1，Origin 不是 localhost/127.0.0.1/[::1] 直接 403。
   解决什么：即便被误暴露也不轻易成为 SSRF/CSRF 跳板。
   我们学什么：我们的 `admitted()` 优先让 connection 服务裁决、退化时比对 Host/Origin，但「无 Origin 时放行」。可补更严策略。不过要小心：DSH 宿主内嵌面板的 Origin 形态未验证，改严之前必须先真机确认，否则会把自己的面板挡在门外——这条先记 P2 不动。

4. **只读/破坏性提示（readOnlyHint / destructiveHint）。**
   它怎么做：每个工具声明有无副作用。
   解决什么：模型不会误判工具的破坏性。
   我们学什么：`review_analysis` 描述里已列出各 action，但没标读写属性。可在描述里补，成本低。

## 第四节 · 知识库：siyuan-note/siyuan（47,432★）

**证据锚点**
- 全名 `siyuan-note/siyuan`。Star **47,432**（2026-11-27 GitHub REST API）。URL：https://github.com/siyuan-note/siyuan
- README 原文逐字：
  > "SiYuan is a privacy-first personal knowledge management system, supporting fine-grained block-level reference and Markdown WYSIWYG."
  > "Notebook folders contain the document data. Ordinary notebooks store `.sy` documents as JSON; encrypted notebooks store them as ciphertext."
  > "Block-level reference and two-way links" / "SQL query embed" / "Protocol `siyuan://`"
  > "Data synchronization through third-party synchronization disks is not supported, otherwise data may be corrupted."
  > "Keep your workspace outside the installation directory; updating SiYuan clears files in the installation directory."
- 独立数据仓组件 `siyuan-note/dejavu` README 逐字：
  > "DejaVu is the component of data snapshot and sync for SiYuan."
  > "Git-like version control" / "File deduplication in chunks" / "Data compression" / "AES Encrypted"
  > "`ID` Each entity is identified by SHA-1"

**优点拆解**

1. **人可读的落盘格式 + 明确的数据目录职责。**
   它怎么做：普通笔记本存 `.sy` JSON，assets/emojis/snippets/storage/templates/widgets/plugins/public 各目录分工。
   解决什么：用户能直接读懂自己的数据，坏了能手工修，不依赖厂商工具。
   我们学什么：我们全部数据在一个 `library/`，被 gitignore，结构私有。v1.8.0 已做「考点包 HTML 人可读导出」和「本机快照」，方向对；但缺一份「数据目录职责说明」让人能手动恢复——这次可以补。

2. **快照做成独立 git-like 版本仓，不是整目录 zip。**
   它怎么做：dejavu 做分块去重、压缩、SHA-1 实体 ID、每次索引生成新 index。
   解决什么：可恢复到任意历史点，同步/备份不损坏主数据。
   我们学什么：我们 v1.8.0 的 `lib/snapshot.js` 只保留最近 5 份全量拷贝，够用但简陋。不升级（本地单机、量小），但要诚实标注「只防改错，不防物理损坏」。

3. **明确告知备份边界，不承诺数据安全。**
   它怎么做：官方文档直说「不支持第三方同步盘，否则数据可能损坏」「工作区放安装目录外，更新会清空安装目录」。
   解决什么：用户不会被「有备份」误导。
   我们学什么：这是诚实边界的范本。我们的快照 UI/说明要同样写清「不防硬盘坏」。

## 第五节 · 学习工具：ankitects/anki（33,064★）

**证据锚点**
- 全名 `ankitects/anki`。Star **33,064**（2026-11-27 GitHub REST API）。URL：https://github.com/ankitects/anki
- README 原文逐字：
  > "Anki is a spaced repetition program."
  > "This repo contains the source code for the computer version of Anki."
- 单一真源官方 `CLAUDE.md` / `AGENTS.md` 逐字：
  > "Protobuf definitions in proto/ that are used by the different layers to talk to each other."
  > "Our build scripts use the .proto files to define our Rust library's non-Rust API. pylib/rsbridge exposes that API, and \_backend.py exposes snake_case methods for each protobuf RPC that call into the API."
  > "Similar tooling creates a @generated/backend TypeScript module for communicating with the Rust backend (which happens over POST requests)."
- 实测 `proto/anki/` 有 **25 个 .proto 文件**（backend.proto / collection.proto / sync.proto / import_export.proto / ankidroid.proto / scheduler.proto 等）。
- 导出/导入契约 `proto/anki/import_export.proto` 逐字：
  > "rpc ImportAnkiPackage(ImportAnkiPackageRequest) returns (ImportResponse);"
  > "message ExportCollectionPackageRequest { string out_path = 1; bool include_media = 2; bool legacy = 3; }"
- 自动备份 `docs-site/automatic-backups.mdx` 逐字：
  > "Anki automatically backs up your collection every time you close Anki or sync ... and by default it stores 30 backups."
- 备份边界 `docs-site/manual/backups.mdx` 逐字：
  > "These include the text on your cards and your scheduling information, but do not include sounds or image files."
  > "Automatic backups can be useful to recover from mistakes, but you should not rely solely on them. Because they are stored on your local device, they will not protect you if your device breaks or is stolen."
- 交换格式 `docs-site/manual/exporting.mdx` 逐字：
  > "A \"packaged deck\" consists of cards, notes, note types, and any sounds or images bundled up into a file ending with .apkg or .colpkg."
  > "`.colpkg` stands for \"Anki Collection Package\". Exporting it will export your entire collection."

**优点拆解**

1. **一份契约生成多端代码，而不是各端手写。**
   它怎么做：`.proto` 是唯一契约，`just check` 生成 Rust API / Python `_backend.py` / TypeScript `@generated/backend`，GUI/CLI/Android 全调同一后端。
   解决什么：四端能力不会各写一遍而漂移。
   我们学什么：我们的 `core/capabilities.js` 是单一真源、已有 `test/core-capability-sync.test.js` 守三端集合一致，方向正确。**这次 DSH 断链恰好证明「单一真源还不够，分派必须也派生」**——action enum 从 capabilities 派生了，但 tool 的 `execute` 分派是手写 if-else，新加的 cards/structure/snapshot 没接上。这是最重要的迁移教训。

2. **事件触发式自动备份 + 分级保留。**
   它怎么做：关闭或同步时自动备份，默认 30 份。
   解决什么：误删可回滚，成本可控。
   我们学什么：我们 v1.8.0 的快照是「改结构前自动留」，比 Anki 的「关闭时留」更聚焦，但导入资料/分析成功这些破坏性操作没留。可评估扩展触发点（P2）。

3. **备份边界写得毫不留情。**
   它怎么做：直说「不含声音图片」「设备坏了 theft 保护不了」。
   解决什么：用户不自欺。
   我们学什么：同 SiYuan，作为诚实边界范本，写进快照说明。

## 第六节 · 知识管理：logseq/logseq（45,724★）

**证据锚点**
- 全名 `logseq/logseq`。Star **45,724**（2026-11-27 GitHub REST API；独立研究员读数 45,722，实时 ±1）。URL：https://github.com/logseq/logseq
- README 原文逐字：
  > "A privacy-first, open-source platform for knowledge management and collaboration"
  > "It focuses on **privacy**, **longevity**, and [**user control**]"
  > "with support for multiple file formats, including **Markdown** and **Org-mode**"
  > "This means that **data loss is possible** so we recommend automated backups or regular SQLite DB backups"
- `logseq/docs/db-version.md` 逐字：
  > "For the desktop, backups are automatically enabled at the `backups` folder inside your graph directory. The last 12 backups are saved."
  > "Export EDN file - Export graph as EDN ... This is the only export type that fully captures a graph's data and is editable."
  > "There are currently 65+ plugins that support DB graphs."
  > "There is an optional [MCP](https://modelcontextprotocol.io/docs/getting-started/intro) server to allow AI applications to connect to a graph."

**优点拆解**

1. **本地优先 + 开放格式，且承认数据可能丢。**
   它怎么做：Markdown/Org-mode 纯文本落盘，README 直写 "data loss is possible" 并推荐自动备份。
   解决什么：用户掌握数据，不被格式锁定；同时不被「绝对安全」的假承诺误导。
   我们学什么：我们的 `library/` 私有格式 + gitignore，是同类风险。考点包 HTML 是「半开放」输出；要补的是「能回导」而不只是「能导出」——v1.8.0 考点包单向导出已诚实标注。

2. **插件 API + CLI + MCP 三入口。**
   它怎么做：插件 API 扩展、CLI 独立运行可接 CI/CD、可选 MCP server 让 AI 连图。
   解决什么：同一份数据多种消费方式。
   我们学什么：我们是桌面/HTTP/DSH 三入口 + CLI，形态对齐。但缺「入口一致性自动验证」——这次 DSH 断链就是三端集合一致、但 DSH 分派没跟上。可加一条判别：三端声明能力与**实调用**一致，不只是集合相等。

## 第七节 · 插件生态分发：obsidianmd/obsidian-releases（23,670★）

**证据锚点**
- 全名 `obsidianmd/obsidian-releases`。Star **23,670**（2026-11-27 GitHub REST API，独立研究员取数）。URL：https://github.com/obsidianmd/obsidian-releases
- README 原文逐字：
  > "This repo is used for hosting public releases of Obsidian, as well as our community plugins & themes directories."
  > "Obsidian is not open source software and this repo _DOES NOT_ contain the source code of Obsidian."
  > "Obsidian will read the list of plugins in `community-plugins.json`."
  > "The `manifest.json` in your repo will only be used to figure out the latest version. Actual files are fetched from your GitHub releases."
  > "If your `manifest.json` requires a version of Obsidian that's higher than the running app, your `versions.json` will be consulted to find the latest version of your plugin that is compatible."
  > "Obsidian will download `manifest.json`, `main.js`, and `styles.css` (if available), and store them in the proper location inside the vault."

**优点拆解**

1. **声明式清单 + 版本兼容协商。**
   它怎么做：`community-plugins.json` 做目录、`manifest.json` 定版本、`versions.json` 做兼容回退、文件从 releases 拉。
   解决什么：去中心化分发且客户端自动选兼容版本，不兼容时降级而不是崩溃。
   我们学什么：我们的 `cordis.patch.yml` 只有 `projectRoot: __AUTO__`，没有版本兼容声明。DSH 版本很多（用户原话「所有 dsh 版本适配」），可评估加一个「最低 core 版本」声明。但这是 P2：当前四级解析已经让所有版本找到 core，没有实际故障。不为适配而适配。

2. **文件清单最小化。**
   它怎么做：只下 `manifest.json`/`main.js`/`styles.css` 三个文件。
   解决什么：分发面小、出错面小。
   我们学什么：反观我们 `APP_FILES` 17 个文件手工列，越列越长越容易漏。再次印证「通配入口 + 目录解析」的方向。

## 第九节 · 交叉结论：哪些是真优点，哪些是噪音

把 9 个项目拆完，按「出现次数 ≥ 3」筛共性，避免被单一项目的个性带偏：

| 共性优点 | 出现项目 | 结论 |
|---|---|---|
| 契约单一真源 + 机器校验 | Anki .proto、MCP Zod、Koishi Schema、Cordis Config、我们 capabilities.js | **真优点，且我们方向对** |
| 配置/依赖错误在加载期暴露 | Cordis ValidationError、Koishi Schema、MCP parse | **真优点，我们弱** |
| 静态资源通配入口 + 路径校验 | Koishi webui、MCP 本机 Origin、我们 DSH exact | **真优点，我们最弱** |
| 明确备份边界、不自欺 | Anki、SiYuan、Logseq | **真优点，我们已做（v1.8.0 快照说明）** |
| 开放/人可读导出 | Anki apkg、Logseq EDN、SiYuan .sy、markmap plain text | **真优点，我们半做（考点包单向）** |
| 事件触发自动备份 | Anki、Logseq | 真优点，我们部分做（改结构前） |
| 声明式版本兼容协商 | Obsidian versions.json | 单一项目，P2 不急 |
| 加密/AES | SiYuan dejavu | 单一项目，本地单机不需要 |
| 热替换不重启 | Cordis replace、Koishi HMR | 单一兴趣点，无实际故障，不做 |

**最重要的迁移教训（这条是本轮拆解的核心价值）**：
Anki 用 `.proto` 做单一真源，但真正保证四端不漂移的是「**各端都从它生成**」。
我们的 `core/capabilities.js` 也是单一真源，action enum 确实从它派生了——
但 DSH 插件的 `execute` 分派是**手写的 if-else 链**，新加的 `cards`/`structure`/`snapshot` 三个 action
在 enum 里声明支持、在分派里却直接落到最后的 `throw '不支持的 action'`。
这不是「单一真源没做」，是「**分派没跟着真源派生**」——
和项目反复踩的「消费端写了、生产端没提供」是同一类病，这次反过来：生产端声明了、消费端没接。
判别测试过去只查「三端集合相等」（声明层），没查「每个声明的 action 真能调用」（行为层），所以假绿。
